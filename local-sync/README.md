# المزامنة المحلية (Local File Sync)

هذه الميزة تُبقي ملف JSON على جهاز المستخدم مطابقًا لحالة Keepit (كل
تصنيف وكل موقع) في كلا الاتجاهين تلقائيًا:

- **دفع (Push):** كل إضافة/تعديل/حذف تصنيف أو موقع، في أي سياق (النافذة
  المنبثقة، صفحة الخيارات، قائمة النقر بالزر الأيمن، اختصار لوحة
  المفاتيح) يُكتب فورًا إلى الملف.
- **سحب (Pull):** يفحص Keepit الملف دوريًا وعند فتح أي واجهة (نافذة
  منبثقة أو صفحة إعدادات)، ليكتشف تغييرات كتبها **متصفح آخر** يشير إلى
  نفس المجلد، ويدمجها في هذا المتصفح تلقائيًا.

هذا الجمع بين الاتجاهين هو ما يجعل فتح الإضافة من متصفح مختلف (Chrome
وEdge على نفس الجهاز مثلًا) يعرض نفس آخر التعديلات، دون أي خطوة استيراد
يدوية.

## لماذا هذا التصميم تحديدًا

- **لا تعديل على الحزمة الأصلية.** `background/index.js` و`options/main.js`
  و`popup/main.js` هي ناتج بناء مضغوط (esbuild) بلا مصدر مرفق، وتعديلها
  يدويًا محفوف بالمخاطر. بدل ذلك، نلتقط كل تغيير من خارجها عبر مراقبة
  `chrome.storage.onChanged` على المفتاح الذي يستخدمه التطبيق أصلاً لحفظ
  كامل حالته: `keepit:state`. هذه هي نقطة الربط الوحيدة لاتجاه الدفع، وهي
  غير جراحية تمامًا (لا نُبدّل أي قيمة، فقط نستمع). اتجاه السحب يكتب إلى
  نفس المفتاح مباشرة، فيُعاد رسم الواجهة تلقائيًا عبر مستمع `onChanged`
  المدمج أصلاً في `main.js` — دون أي حاجة لمعرفة داخل الحزمة أو استدعائها.

- **الكتابة والقراءة الفعليتان تحتاجان مستند DOM حقيقي.** File System
  Access API (`showDirectoryPicker`, `FileSystemDirectoryHandle`) غير
  متاحة داخل service worker. لذلك تتمّان إما من صفحة الخيارات/النافذة
  المنبثقة مباشرةً (لهما DOM حقيقي أصلاً)، أو من مستند `offscreen` خفي
  ينشئه service worker عند الحاجة — وهو ما يجعل المزامنة (دفعًا وسحبًا)
  تعمل حتى لو كانت كل الواجهات مغلقة.

- **لا يوجد "مراقب ملف" أصلي في المتصفح.** File System Access API لا
  توفّر حدثًا يُطلَق عند تغيّر ملف على القرص من خارج الصفحة. لذلك اتجاه
  السحب يعتمد على **فحص دوري** (`chrome.alarms`، كل دقيقتين) بالإضافة إلى
  فحص فوري عند بدء تشغيل المتصفح، وعند فتح صفحة الإعدادات أو النافذة
  المنبثقة. هذا يعني أن السحب "شبه فوري" عمليًا (خصوصًا عند فتح أي واجهة)
  وليس فوريًا رياضيًا.

- **لا حلقة تغذية راجعة.** بعد كل سحب ناجح، يصبح محتوى الملف مطابقًا لما
  في `keepit:state` بنيويًا، فلا يكتشف الفحص الدوري التالي أي اختلاف
  ويتوقف عن إعادة الدمج (`local-sync/compare.js` يقارن المحتوى الفعلي —
  التصنيفات والمواقع — لا حقولًا عرضية كالمعرّفات أو الطوابع الزمنية التي
  تُولَّد من جديد في كل تحويل).

- **إذن الوصول للمجلد محلي بحت، ومستقل لكل متصفح.** يُخزَّن
  `FileSystemDirectoryHandle` في IndexedDB الخاص بأصل الإضافة فقط (وليس
  `chrome.storage.sync`)، فلا يُرفَع أي شيء عن بنية ملفات الجهاز إلى أي
  حساب. لكن هذا يعني أيضًا أن كل متصفح (Chrome، Edge، ملف تعريف مختلف...)
  يحتاج منح إذن مستقل لنفس المجلد — قيد أمان من المتصفح نفسه لا يمكن
  تجاوزه، وليس قصورًا في الميزة.

## تدفق العمل: الدفع (Push)

```
تغيير في التطبيق (أي سياق)
   → chrome.storage.local.set({'keepit:state': ...})   [كود أصلي غير مُعدَّل]
   → chrome.storage.onChanged                           [background/local-sync-sw/controller.js]
   → تجميع قصير (debounce 250ms)
   → ضمان وجود مستند offscreen
   → chrome.runtime.sendMessage(MSG_WRITE)              [offscreen/offscreen.js]
   → local-sync/writer.js
       → قراءة FileSystemDirectoryHandle من IndexedDB
       → queryPermission → إن لم تكن "granted": فشل صريح، لا إعادة محاولة صامتة
       → بناء صيغة "تصدير" Keepit القياسية (local-sync/export-schema.js)
       → كتابة/استبدال الملف
   → تحديث keepit:fsSync (وقت آخر نجاح / آخر خطأ) لتعرضه صفحة الإعدادات
```

## تدفق العمل: السحب (Pull)

```
منبّه دوري (كل دقيقتين) أو بدء تشغيل المتصفح أو فتح واجهة
   → ضمان وجود مستند offscreen (أو تنفيذ مباشر من صفحة الإعدادات/النافذة المنبثقة)
   → local-sync/reader.js
       → قراءة الملف؛ عدم وجوده لا يُعامَل كخطأ (لا شيء لسحبه بعد)
       → local-sync/import-schema.js: تحقّق من الشكل العام
   → local-sync/compare.js: هل يختلف محتوى الملف فعليًا عمّا في هذا المتصفح؟
       → لا؟ توقف هنا (لا كتابة، لا توليد معرّفات جديدة)
   → local-sync/import-schema.js: تحويل تصنيفات الملف إلى الشكل الداخلي
     (معرّفات جديدة عبر crypto.randomUUID، pinned:false، order متسلسل)
   → globalThis.KeepitDedup.mergeCollections(...)   [shared/dedup.js، نفس منطق
     الاستيراد اليدوي المدمج في التطبيق تمامًا]
       → وضع "دمج": الأساس = تصنيفات هذا المتصفح + الجديد من الملف
       → وضع "استبدال": الأساس = [] (الملف وحده هو المرجع الكامل)
   → chrome.storage.local.set({'keepit:state': ...})
   → تحديث keepit:fsSync (وقت آخر سحب / آخر خطأ سحب)
```

## وضعا الدمج عند السحب

| الوضع | يضيف الجديد؟ | ينقل الحذف؟ | خطر فقدان بيانات |
|---|---|---|---|
| **دمج (افتراضي)** | نعم | لا | لا يوجد أبدًا |
| **استبدال (متقدّم)** | نعم | نعم | نعم، إن كانت هناك إضافات محلية لم تُزامَن بعد |

الافتراضي **دمج** لأنه لا يحذف أي شيء بصمت أبدًا — أسوأ ما يحدث هو أن
حذفًا تمّ في متصفح آخر لا ينتقل تلقائيًا لهذا المتصفح. **استبدال** ينقل
الحذف أيضًا، لكنه يجعل الملف "الحقيقة الوحيدة" فعليًا؛ لا يُنصَح به إلا
لمن يعمل من متصفح واحد فعليًا في كل مرة.

## الإعداد على أكثر من متصفح

1. افتح صفحة الإعدادات في **كل** متصفح تريد المزامنة بينه وبين غيره.
2. اختر **نفس المجلد بالضبط** (نفس المسار الفعلي على القرص) في كل متصفح.
   هذا يتطلب نقرة مستخدم فعلية في كل متصفح على حدة — قيد أمان من المتصفح
   نفسه، لا يمكن أتمتته أو تجاوزه من الكود.
3. من تلك اللحظة، الدفع والسحب يعملان تلقائيًا في الخلفية بلا أي خطوة
   يدوية إضافية.

## حدود معروفة (يُفضَّل معرفتها بدل افتراض كمالها)

1. **Chromium فقط.** File System Access API وchrome.offscreen غير
   متوفرتين في Firefox حاليًا. اللوحة تكتشف ذلك (`showDirectoryPicker in
   window`) وتعرض رسالة توضيحية بدل عناصر تحكم لا تعمل.
2. **أول ربط يحتاج نقرة مستخدم فعلية، في كل متصفح على حدة.** لا يمكن لأي
   كود (بما فيه مستند offscreen) طلب إذن جديد دون بادرة مستخدم حقيقية.
   إن انتهى الإذن الدائم لأي سبب، يظهر زر "منح الإذن مجددًا" بدل محاولة
   صامتة قد تفشل بصمت.
3. **لا يُحدَّد اسم/مسار المجلد برمجيًا.** المستخدم يختار المجلد يدويًا
   (نافذة نظام التشغيل)؛ الإضافة لا "تعرف" مسار مشروعك تلقائيًا.
4. **السحب دوري وليس فوريًا رياضيًا.** بلا مراقب ملفات أصلي في المتصفح،
   أقصى تأخير للفحص الدوري في الخلفية دقيقتان (`PULL_INTERVAL_MINUTES`)؛
   فتح أي واجهة (نافذة منبثقة أو إعدادات) يُشغّل فحصًا فوريًا إضافيًا.
5. **وضع "دمج" لا ينقل الحذف.** حذف تصنيف/موقع في متصفح A لن يختفي
   تلقائيًا من متصفح B إلا إذا فعّلتَ وضع "استبدال" في B (بعلمك بمخاطره).
6. **تعارض التعديل المتزامن غير مُدار بذكاء.** إن عدّلتَ نفس التصنيف في
   متصفحين قبل أن تتم أي مزامنة بينهما، ستُدمَج التصنيفات حسب الاسم
   (والمواقع حسب الرابط) لا حسب "مَن عدَّل أخيرًا" — هذا سلوك مقصود
   لتفادي فقدان بيانات، لا خوارزمية "أحدث نسخة تفوز" (last-write-wins)
   على مستوى الحقل الواحد.
